# Multi-tenant workspace model and Agent/Contact rename

Roadly moves from one-deployment-per-customer to a single shared platform serving many customer businesses at once, the way Vercel, Notion, or Slack do. A `Workspace` model now represents one customer business (tenant); `Contact` (renamed from `EndUser`) and `FeatureRequest` are scoped to a `workspaceId`, and `Contact.externalId` — the host-supplied identity upserted on every widget request — is unique per `(workspaceId, externalId)` rather than globally, since two unrelated businesses' host apps can legitimately both send `externalId: "user_123"`. `FeatureRequest.workspaceId` is denormalized (not derived by joining through `author`) because the two most frequent queries — the widget's public list and the Roadmap Board's per-status list — are both workspace-scoped list queries; a composite `@@index([workspaceId, status])` serves both. `Vote` deliberately gets no `workspaceId`: no query needs workspace-wide vote lookups (vote analytics is explicitly out of scope per `project-overview.md`), and Prisma/Postgres can't enforce cross-FK consistency (that a Vote's `Contact` and `FeatureRequest` share a workspace) without triggers — that check belongs in the service layer once the votes service exists, which it doesn't yet. This supersedes `docs/adr/0001-single-tenant-deployment.md`. The embeddable widget resolves its tenant via a `Workspace.widgetKey` sent at `Roadly.init(...)` — a separate field from `Workspace.id`, mirroring how ADR 0002 already kept `externalId` separate from a Contact's internal id, so the key can rotate later without touching any foreign keys. This is a data-model change only; no self-serve signup/onboarding flow exists yet, so workspaces are created manually (seed data or an admin script) until dashboard auth is built.

The admin dashboard identity (renamed `Agent`, previously `TeamMember`) is a **global** identity, not scoped to a single workspace: one person can administer multiple businesses' roadmaps (e.g. an agency running several clients' boards) under one login. Rather than a direct `workspaceId` foreign key, `Agent` links to `Workspace` through a `WorkspaceMember` join table (`@@unique([workspaceId, agentId])`), so `Agent.email` stays globally unique — the natural shape for one person, one login, many workspace memberships. `WorkspaceMember` carries no `role` field yet; MVP is still single-role per `architecture.md`'s Auth section, and a role only gets added once multiple roles actually exist.

Both identity models are renamed to fit the now-explicitly-multi-tenant, CRM-shaped product: `TeamMember` → `Agent` (the platform operator managing one or more businesses' boards) and `EndUser` → `Contact` (a business's own end customer, interacting through that business's widget). `docs/adr/0002-separate-enduser-teammember.md`'s original reasoning for avoiding the bare term `User` — it was the ambiguous collapsed model the split fixed — still holds, and `Agent`/`Contact` keep avoiding it rather than reintroducing it. `Vote.userId`/`user` is renamed to `contactId`/`contact` for the same reason: the old field name baked in "user," which every doc in this project treats as a banned term. The identity split itself (credentialed dashboard identity vs. no-credential widget identity keyed by a host-supplied id) is unchanged from ADR 0002 — only the names and the workspace scoping change.
