# Widget identity: unsigned install first, signed identity opt-in

`widgetKey` is public, so today anyone holding it can call `POST /widget/contacts` with any `externalId` and get back that Contact's `id`, `name` and `email`. That `id` is the only credential for acting as the Contact, and it never expires. The "identified but unverified" trade-off in `architecture.md` undersold this: it allows impersonation and exposes PII. We considered making the widget read-only without a signed token, but chose a two-step install instead, as Intercom does: a customer pastes the snippet and sees the widget working, then a Secure step on the Install page explains the risk and sets up signing. Seeing it work before any backend change is worth keeping an unsigned mode, so enforcement is opt-in per Workspace, and the mode's risk is contained rather than removed. In an unsigned Workspace, anyone who knows a user's `externalId` can still act as that user; only enforcement fixes that.

Both modes end in the same Roadly session token, so the guard keeps one path. `POST /widget/session/unsigned` takes `{ externalId, name, email }` and `POST /widget/session/signed` takes the host's token. Each returns a bearer session token of about 1h, signed with `WIDGET_SESSION_SECRET`, and no PII or `externalId`. It replaces `x-contact-id` and `POST /widget/contacts`. It's a bearer token held in memory rather than a cookie because the widget calls our API from other companies' sites, where browsers often block third-party cookies. The guard still looks up the Contact on each request, so deleting a Contact ends their session immediately. The host supplies `getToken` rather than a static token because an open tab outlives any short expiry.

Trust comes from the signature, not from `widgetKey`, which only selects the Workspace whose secret to check against. Each Workspace has its own secret, separate from `widgetKey`, generated in the dashboard and shown once. It must be recoverable to verify signatures, so it's stored encrypted with AES-256-GCM under `IDENTITY_SECRET_ENCRYPTION_KEY`. Rotation keeps the old secret valid for 24h. Tokens are pinned to HS256, and any token valid for more than 1h is rejected. Only `user_id` and `exp` are required, because a security step developers finish protects more users than a stricter one they skip; `exp` stays required because a token without it can be replayed forever if stolen. `name` and `email` are optional, and a claim left out never overwrites a stored value. `aud` is dropped because each secret is used only for this.

Making `name` and `email` optional in tokens means `Contact.name` and `Contact.email` become nullable, and verifying a person doesn't verify their stored email: a Contact created unsigned with a fake email could later be verified by a token carrying only `user_id`. So `Contact` gets two fields: `verifiedAt`, set by any signed token, and `emailVerifiedAt`, set only when the token includes `email`. Anything sent to a Contact's address, such as status-change notifications, must require `emailVerifiedAt`. The unsigned route still requires `id`, `name` and `email`, so agents get names from the first install. Once a Contact is verified, the unsigned route refuses its `externalId`, which protects users during rollout, before enforcement is on.

When `requireSignedIdentity` is on, the API rejects the unsigned route, and existing unsigned sessions stop working on their next request. It can't be turned on until a verified Contact exists, so a Workspace can't lock out its own users by mistake. If a host later stops sending valid tokens, the widget goes read-only rather than falling back to unsigned. Contacts created before enforcement keep their history, because a signed token can correct a name or email but can't tell which earlier activity was real. Agents see an "Unverified" label on unverified authors, since vote counts and names in an unsigned Workspace can't be fully trusted.
